# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Evidence-grounded diagnosis | Compare the plan's problem statement and proposed explanation with the issue context, repro-evidence steps, observed output, and any supplied source excerpts. | Pass when the plan addresses the behavior actually demonstrated and its explanation does not contradict the evidence. An unconfirmed cause may remain a hypothesis if the plan identifies how it will be checked before relying on it. A diagnosis of a different failure does not pass. | required |
| Cause-directed change | Compare the proposed intervention and its stated mechanism with the reproduced trigger, implicated code or documentation, and relevant maintainer analysis. | Pass when the proposed change explains how it resolves the issue's demonstrated behavior at the responsible boundary. Hiding an error, suppressing a failing test, or bypassing the affected path does not pass unless the evidence and requested outcome establish that behavior as the intended solution. | required |
| Bounded scope | Read the plan's intended outcome, implementation actions, named files or areas, exclusions, and deviation notes against the issue's requested outcome. | Pass when all proposed changes contribute to one issue-related outcome. Necessary supporting edits and regression checks are allowed; unrelated cleanup, speculative features, or an open-ended rewrite are not. Judge the relationship among changes, not the number of files or presence of a scope heading. | required |
| Executable approach | Read the plan's implementation actions and order against the repository facts, supplied source locations, prerequisites, and stated unknowns. | Pass when another contributor can identify the starting location, intended modification, and material dependencies without inventing the core approach. A concrete investigation step may resolve an unknown if it states what evidence will choose the next action; "investigate and fix" alone is insufficient. Do not require exact line numbers when a file, symbol, or area identifies the work unambiguously. | required |
| Decisive verification | Compare the proposed verification input, trigger, execution path, and expected observation with the Unit 2 repro evidence and the intended outcome. | Pass when the plan defines an observable check that would distinguish the reported failure from the intended result after the change. Re-running the repro or an equivalent check through the affected path is sufficient. Tests that cannot exercise the defect, assertions that only confirm a mock's programmed return value, and "run tests" without a relevant observable result do not pass. For a documentation mismatch, direct inspection and the documented setup operation may be decisive without starting the application. | required |
| Honest uncertainty and deviations | Compare the plan's certainty claims, assumptions, risks, decision points, and any deviation notes with the issue, repro evidence, repository facts, and available implementation record. | Pass when material unknowns are identified rather than asserted as proven, and the plan explains how uncertainties affecting the approach will be resolved or bounded. When a deviation is reported or visible in the supplied evidence, the plan records what changed and why and identifies any effect on scope or verification. Do not require a completed build or a deviation before implementation has occurred. | required |
| Thread and repository alignment | Compare the draft plan comment and detailed plan with the issue discussion, maintainer requests, repo-facts block, contribution rules, and applicable disclosure or template requirements. | Pass when the comment communicates the actual intended change and verification, agrees with the detailed plan, and honors relevant maintainer constraints and repository requirements. If a required disclosure applies to this comment, it must be present. A different proposal may pass if it directly acknowledges the earlier request, explains the evidence for the alternative, and seeks any required agreement rather than presenting a prohibited change as settled. | required |

## Verdict rule

Accept only when every required check passes. Reject when any required check fails or is unclear. Preferred checks, if added later, never change the verdict.

Use fail when the available evidence demonstrates a violation or a necessary element is absent from the supplied plan package. Use unclear when a material fact cannot be established from the available evidence or a required source cannot be accessed. Do not invent missing facts.

Judge readiness to post and build, not whether the change has already been implemented. Before implementation, missing after-results or deviation history are not failures. For an updated package after a deviation, assess the current plan and the recorded change together.
