# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Maintainer activity | `repo-facts` block: the maintainer first-response sample, including issue dates, response delays, and whether an issue opener is identified as an owner, member, or collaborator; the last 5 default-branch commit dates and authors | Pass if the bundle shows at least one owner, member, or collaborator opening an issue, commenting on an issue, or making an identifiable default-branch commit within 180 days before the capture date. Fail if all dated maintainer activity is older than 180 days. Mark unclear if the bundle provides no dated activity tied to an owner, member, or collaborator. | required |
| Repository in use | `repo-facts` block: dates of the last 5 default-branch commits and repository activity information | Pass if at least 3 of the last 5 default-branch commits are dated within the last 180 days. Fail if fewer than 3 are within that period. Mark unclear if the relevant commit dates are missing. | required |
| Newcomer scope | `issue body`: requested change, affected component, and described problem; `repo-facts` block: repository and component information; `comment thread`: maintainer clarifications | Pass if the issue identifies a concrete problem, feature, or behavior within this repository and the requested work appears bounded to one component or related area. Do not fail solely because reproduction steps, implementation details, or the expected behavior are incomplete. Fail if the issue explicitly requires a repository-wide redesign, unrelated changes across multiple components, or work outside the repository. Mark unclear only when neither the affected area nor the requested work can be identified. | required |
| Issue availability | `repo-facts` block: current assignees and linked PRs, including whether each PR is open or closed; `comment thread`: dated explicit claims and work-in-progress statements | Pass if there is no current assignee, no open linked pull request, and no explicit claim or work-in-progress statement within 90 days before the capture date. A closed pull request does not fail this check. A claim older than 90 days without a current assignee, later work update, or open linked pull request is stale and does not fail this check. Fail if there is a current assignee, an open linked pull request, or an explicit claim or work update within 90 days before capture. Mark unclear if the status or date of a possible claim or linked pull request is missing. | required |
| Project policy fit | `repo-facts` block: the contribution-policy text and its named section; `issue body` and `comment thread`: any additional maintainer restrictions on contribution methods | Pass if the contribution policy does not explicitly prohibit AI-generated code or documentation. Fail if the policy states that AI-generated code or documentation is not accepted, because this course uses an AI-assisted contribution workflow. Also fail if a maintainer explicitly prohibits the contribution method required by the course. Mark unclear only if the policy uses ambiguous language about whether AI-generated contributions are accepted. | required |
| Reproduction clarity | `issue body`: reproduction steps, observed behavior, expected behavior, and environment or component details; `comment thread`: maintainer clarifications | Pass if the issue body or comment thread provides an observable problem and an expected result, plus enough steps or component information for a contributor to investigate without requesting basic clarification. Fail if the issue is only a vague report or feature idea with no observable behavior. Mark unclear if the evidence is insufficient. | preferred |

## Verdict rule

Accept an issue only if every required check passes. Reject an issue if any required check fails. An unclear result on any required check counts as a failure. The preferred Reproduction clarity check never changes the accept or reject verdict; it only helps rank issues that are accepted.
